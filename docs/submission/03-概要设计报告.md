# 概要设计报告

## 1. 设计目标

系统接收一个 DAT、裸二进制或网络抓包文件，根据输入实际具备的证据选择分析路径，并输出机器可校验的中间产物和人类可读报告。总体目标包括：

1. 支持数据包识别、解码、统计分析、特征提取、内容恢复和行为分析。
2. 对未知格式给出可解释候选，不把统计相关性表述成协议真值。
3. 对标准协议复用 TShark，对项目特有的证据组织、边界推断和验收自行实现。
4. 保证结果可重复、失败可诊断、产物不可被静默覆盖。
5. 支持三人分线开发以及独立验收。

## 2. 系统边界

输入包括普通字节文件、PCAP/PCAPNG、显式 profile，以及可选的 TShark 路径。分析入口不接收测试 truth 或分类标签。输出包括模块 JSON、二进制派生产物、确定性 Markdown 报告、运行清单和独立验收结果。

系统不负责自动获取未知数据集、不自动回放恶意流量、不在无密钥条件下承诺解密 TLS/SSH，也不把模型输出作为独立证据。实时接口采集属于辅助数据制作功能，需要另装 Npcap，不是读取已有抓包的必要条件。

## 3. 总体架构

```text
                  +------------------------+
Input + Profile ->| A: scripts/analyze.py  |
                  +-----------+------------+
                              |
          +-------------------+-------------------+
          |                                       |
  M01 -> M02                               M01 -> M07
   |                                           |
   +-> M03 -> M04 -> M05 -> M06                +-> HTTP ranges -> M08
   |
   +-> M09 -> M10 -> M11
          \         |         /
           +--------+--------+
                    M12
                     |
              run_manifest.json
                     |
          C: verify_acceptance.py -> PASS/FAIL
```

系统不是固定串行流水线。profile 定义实际任务图：裸字节可以执行 M01/M02/直接 M08/M12；有连续消息来源时进入 M03-M06；已确认抓包时进入 M07/M09-M11；满足严格 HTTP 条件时才建立 payload-source 并进入正文恢复。

## 4. 模块划分

| 模块 | 职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| M01 | 内容识别、抓包解析、流与双向字节流重组 | DAT/BIN/PCAP/PCAPNG | `result.json`、原始/stream artifact |
| M02 | 字节频率、熵、字符与窗口统计 | 字节文件 | `features.json` |
| M03 | 显式消息分帧 | 字节流、规则 | `framing.json`、消息 artifact |
| M04 | DBSCAN 消息聚类 | M03 | `clusters.json` |
| M05 | 代表消息参考对齐 | M03+M04 | `alignments.json` |
| M06 | 字段区间和长度关系候选 | M05 | `format.json` |
| M07 | 标准协议识别和字段证据 | M01+抓包 | `protocols.json` |
| M08 | 有界解码、解压与内容恢复 | 字节或 payload-source | `recovery.json`、恢复 artifact |
| M09 | 流级统计特征 | M01 | `flow_features.json` |
| M10 | 非语义行为规则 | M09 | `behaviors.json` |
| M11 | 分组训练、评估与无标签推理 | 固定特征行 | `classification.json`、`model.joblib`、prediction/evaluation |
| M12 | 证据归一化与报告 | M01-M11 产物 | `report.md`、`report_manifest.json` |

## 5. 数据与接口设计

所有主产物使用 JSON，Schema 位于 `research/`。公共字段包括 `schema_version`、`source`、`status`、`parameters`、`metrics` 和 `warnings`。上游引用至少包含 artifact 路径与 SHA-256。字节范围统一采用从 0 开始的半开区间 `[start,end)`，时间以秒为单位，方向默认使用 `node0_to_node1` / `node1_to_node0`，只有存在独立角色证据时才称客户端或服务端。

统一运行清单使用 artifact 数组而非模块字典，因此同一模块可以保存多个正文或流实例。`(module, instance_id)` 唯一标识实例，scope 记录 stream、direction、payload source 等范围。

## 6. 运行与部署设计

- 核心运行环境：Python 3.11+。
- 必需依赖：jsonschema；M11 训练依赖 scikit-learn/joblib。
- 可选外部工具：Wireshark/TShark/Capinfos，用于新鲜抓包解析。
- 可选外部服务：DeepSeek API，仅在显式 `--invoke-model` 时调用。
- 临时输出：`tmp/`；正式冻结数据：`data/acceptance/`；报告：`reports/`。

每个输出目录必须事先不存在。模块采用 staging 目录生成，Schema 和引用检查通过后再原子发布。打包脚本只复制 Git 已追踪文件，生成带 commit、文件长度和 SHA-256 的 `PACKAGE-MANIFEST.json`。

## 7. 安全设计

1. 输入路径、来源哈希和内部引用在消费前重新校验。
2. 解码/解压设置输入、输出、递归深度和膨胀率上限，防止资源耗尽。
3. 模型证据文本按不可信数据处理，禁止其改变系统指令或引用不存在的证据。
4. API key 不写文件；本地第三方二进制和临时目录不打包。
5. 公共恶意协议样例仅离线解析，不执行、不回放。

## 8. 可扩展性

新增模块时需同时提供生产者、严格 Schema、README、单元测试和 M12 适配器。新增数据集需记录来源、许可、获取时间、大小和 SHA-256。新增分类任务需使用独立标签维度和 group 定义，不与现有 application 或 VPN 状态标签混用。
