# 三人团队验收协作 - Plan

## Goal and Authority

主要读者是分别执行A/B/C工作的三个Codex任务。先读 `docs/acceptance/codex-execution-contract.md`，再读自己的 `docs/acceptance/role-a.md`、`role-b.md` 或 `role-c.md`；按角色入口指定的顺序加载本计划。不要默认从头读取所有研究资料。

执行控制以依赖和验收门禁为准。下文的会议、时刻、人时、姓名和占比属于人类团队安排，不是Codex休眠、等待到点、虚构成员信息或提前宣告完成的依据。每个角色要实现并验证自己的工作包，不能把本文件误当成只需编写文档的任务。

三人共同交付可现场运行的 DAT 分析作品：协议识别、可核验原文恢复、行为分析、新输入分类、实际大模型解释和证据报告形成闭环，并备齐课程提交材料。

本计划是团队执行分工，承接 `docs/plans/2026-09-10-1827-feat-acceptance-closure-plan.md` 的 R1～R9、U1～U7、Verification Contract 和 Definition of Done；不降低其中的验收要求。A/B/C表示三个Codex执行角色，各由一位成员操作和确认。人类可用时间尚未确认，排期仅用于安排交付。

PDF 记载 9 月 12 日验收、每组 15 分钟、当晚 20 点前提交。安排以 9 月 11 日晚形成冻结版本为目标，新增功能不能挤占最后的联调和演练。

## Shared Contract Before Coding

G0由A形成接口契约和样例，B/C验证自己消费和生产的部分并发布接收记录。下面是待实现的团队接口，不声称当前代码已经支持。

| 交接对象 | 生产者 → 消费者 | 必要信息 | 接收标准 |
|---|---|---|---|
| 采集场景 | B → C | 本地服务启动命令、下载/上传/周期请求操作、原文、预计HTTP封装 | C可以独立采集，原文预先固定 |
| 数据清单 | C → A/B | `sample_id`、输入相对路径、SHA-256、来源类型、采集任务ID；标签/真值单独保存 | 分析器只收到输入清单，不收到测试标签与期望恢复文件 |
| M01结果 | B → A/C | 既有packet/flow/stream ID、方向、时间与字节artifact | 通过既有Schema及引用校验；双方使用同一个M01产物 |
| 载荷来源 | B → A | 来源artifact及哈希、流/方向/消息ID、`[start,end)`、协议与封装依据、提取状态 | 每个正文可追到重组流；chunked等离散来源用多个区间，不能伪装单一连续范围 |
| 行为分类 | C → A | 输入/流ID、任务维度、特征版本、模型哈希、预测类别、分数及拒识原因 | 新输入无标签也能推理；训练评估与新输入预测分开保存 |
| 运行清单 | A → C | 本轮输入哈希、全部artifact实例/路径/哈希、版本、参数、阶段状态 | C无需读取控制台文字即可检查结果 |
| 验收结果 | C → A | R-ID、pass/fail/not_applicable、断言、证据引用、汇总退出码 | 核心正例缺恢复/分类/模型任一项均不能通过 |

必须保留多实例：同一模块针对多个流生成的结果不能由 `{"M08": path}` 单键覆盖。A采用包含 `module`、`instance_id`、路径、哈希和scope的artifact列表，逐项校验并交给M12；为原有单artifact调用保留兼容适配。

G0结束条件是最小合法和失败JSON样例通过生产者与消费者检查；在等待接口时先做不依赖新字段的本线工作。Mock样例用于解耦开发，不作为最终验收结果。

## Person A Work Package

### A1. Environment and executable skeleton

- 对应U1环境部分、U2；预计2～3人时。核对实际Python、TShark、依赖版本，提供会话内可复现启动方法，修正文档过时说明。
- 新建 `scripts/analyze.py`；读取一个输入及分析profile，调用现有模块函数，生成运行清单与总报告链接。训练不放入每次分析路径。
- 实现新输出目录、原子发布、失败阶段状态及多实例清单。不得用忽略异常使整轮变绿。
- 测试归属：`experiments/tests/test_acceptance_pipeline.py`。测试输入不存在、目录已存在、损坏artifact、多个流和上游异常。
- 交付给B/C：可运行入口、profile样例、运行清单正反样例、实测命令。此时可以部分能力未接，但必须标明。

### A2. Actual model and traceable report

- 对应U5；预计3～4人时。第一小时就核实本地模型运行条件，不能等分类与还原都完成后才找模型。
- 新建 `experiments/M12/model_adapter.py`，规定输入输出、超时、长度限制、模型身份和引用检查；用已有公开样例证据完成第一次真实调用，再接B/C真实新产物。
- 修改M12多来源适配及报告：事实、模型解释、限制、原文件/恢复文件/分类结果可定位。模型引用存在不等于语义正确，由B检查至少一份完整正例解释。
- 测试归属：`experiments/M12/tests/test_model_adapter.py`。包括无效引用、超时、格式错误、证据文本夹带指令及无依据结论。
- 交付：真实调用记录、身份/提示版本、输入摘要哈希、响应与引用核验结果；Mock不满足交付。

### A3. Integration and release

- 对应U2剩余部分、U7；预计3～4人时。整合B的多来源恢复、C的新输入推理和独立验收工具；运行主链并修复集成问题。
- 写技术原理总览、概要设计、安装使用说明及PPT总览页；生成便携目录与打包脚本，检查移动后引用。
- A为集成负责人，负责接收和定位跨模块问题；根因在B/C模块时仍由对应负责人修复，不把所有缺陷压到A。

## Person B Work Package

### B1. Capture service and protocol/body extraction

- 对应U1采集服务部分、U3；预计3～4人时。提供自控HTTP服务与固定内容，让C可进行下载、上传、周期请求采集；禁止使用恶意公共样例回放采集。
- 新增 `scripts/acceptance_http_server.py` 和 `experiments/payload_sources.py`；把Content-Length正文、chunked正文及方向映射为可追溯来源。
- 保留M01/M07既有识别证据，明确HTTP封装来自解析。两方向、多响应均须遍历，重组不完整不能宣称完整正文。
- 测试归属：M07/M08本模块测试及 `experiments/tests/test_payload_recovery_pipeline.py`；覆盖分段正文、双向、多响应、截断、重传/缺口。
- 第一批交付：C可采集的服务、A可消费的来源清单、单个HTTP正文提取样例。

### B2. Recover bytes and connect structural analysis

- 对应U3；预计3～4人时。先使普通HTTP原文恢复通过，再接gzip/zlib和chunked；保留来源范围和转换链。
- 将原生长度流接M03～M06，核对分帧覆盖、对齐重建与字段假设。使用人工规则就明确写人工规则；不通过添加假长度头冒充原生推断。
- 对网络正例，在适用消息集合上输出结构结果；已知协议解析与未知格式统计候选分开解释。
- 交付：非空恢复文件、恢复JSON、协议JSON、结构结果和重跑命令；由C独立验证原文哈希。

### B3. Negative cases and technical explanation

- 对应U3边界、U7；预计2～3人时。补随机流、损坏正文、无密钥密文、超限输入测试；Brotli现阶段如实报不支持。
- 写协议与内容恢复详细设计、来源映射示例及PPT技术页；审查A报告的证据语义；录制恢复步骤片段。
- U6的UDP/额外协议默认延期，只有核心门禁全绿且还有时间才由B/C配合扩展。

## Person C Work Package

### C1. Freeze data and expected outcomes

- 对应U1；预计2～3人时。接收B服务，负责抓包工具和采集命令；先交一个完整主样例，随后扩充分类采集集。
- 新建 `scripts/capture_acceptance_samples.py`、`data/acceptance/manifest.json` 和独立truth目录；保存真实时间、动作、分组、原文哈希和许可/来源。
- 下载、上传、周期请求每类目标至少6个独立任务，划分4个训练、1个验证、1个最终测试；这是最低开发样本量，不能据此宣称普适分类效果。固定随机种子只用于可复现，不代替采集独立性。
- 周期请求应在同一被分类流中体现时序；若服务每次新建连接，必须改采集方式或明确实现跨流聚合，不能把看不到周期的单流强标为周期行为。
- 文件大小、正文内容和会话参数在类别间交叉变化；同一原文或近重复任务不跨分区。数据ID、文件路径、标签、采集说明不得作为分类特征。
- 交付：主例、裸流与负例的冻结清单；完整分类分区稍后交付。测试位于 `experiments/tests/test_acceptance_manifest.py`。

### C2. Features, training and unseen-input prediction

- 对应U4；预计3～4人时。新增M09到固定特征行适配，完成训练、验证和模型导出，再实现 `experiments/M11/predict.py`。
- 现有M11内部选择训练/测试拆分；本轮需新增显式分区支持或等价入口，严格使用C1冻结的分区，不能把最终测试数据交给内部随机重拆。
- 验证集用于参数和拒识阈值选择；最终测试冻结后一次评估。若据最终结果修改方案，应另采独立测试集并记录旧结果，不能反复优化同一测试集。
- 测试位于 `experiments/M11/tests/test_predict.py` 和 `experiments/tests/test_behavior_acceptance.py`：无标签输入推理、模型哈希/特征版本不符、缺值、分组重叠与缺依赖。
- 交付：模型、特征定义、训练/验证/测试分组、混淆矩阵、逐类指标、macro-F1、多数类基线和新DAT预测JSON。模型分数写清含义，不当作校准后的置信度。

### C3. Independent gate and evidence package

- 对应U2验证部分、U7；预计3～4人时。实现 `scripts/verify_acceptance.py`，读取A运行清单和独立truth；检查恢复、分类、模型调用及证据引用。
- 故意把恢复文件清空、把模型调用改为跳过、去掉分类结果，确认正例门禁失败。验收脚本不能只看顶层status。
- C验证B恢复；A验证C分类；B验证A解释。最终C汇总，不由任何成员单方面为自己的关键输出签字。
- 写测试报告和数据说明，汇总三人PPT、分工表及贡献记录；整理缺陷列表和证据索引。材料中的指标只从保存的正式结果读取。

三线各预计8～11人时，总计24～33人时，不含大模型安装/下载等不可预估等待。三人共同联调与演练另留2～3小时；这些估计用于发现超载，不是完成承诺。

## Acceptance Cases and Signoff

| 用例 | 主要覆盖 | 负责实现 | 独立验收人 | 必须保留的证据 |
|---|---|---|---|---|
| AC01 自采HTTP DAT主正例 | 原计划F1、R1～R6 | A/B/C各自链段 | 三人交叉 | 协议字段、结构结果、恢复哈希、行为/分类、真实模型解释、总报告 |
| AC02 原生长度裸流 | F2、R2/R7/R9 | B | C | 原生规则来源、字节覆盖、对齐重建、字段候选、明确无网络元数据 |
| AC03 独立采集分类测试 | R4/R7 | C | A | 分组隔离、模型哈希、无标签推理、真实标签独立评估、误分记录 |
| AC04 随机/损坏/密文 | F3、R6/R9 | B；A接入 | C | 未知/损坏/无密钥原因；无伪协议/伪恢复 |
| AC05 缺工具/缺模型/缺分类 | R6 | A/C | B | 正例验收失败，已有事实报告仍可查看 |
| AC06 输出篡改与多来源 | R1/R6 | A/B/C | 非实现者 | artifact哈希不匹配拒绝；多流/双方向证据均可定位 |
| AC07 新目录解压复跑 | R8 | A | B在演示机操作，C记录 | 环境版本、完整路径、同一恢复哈希、录像和运行命令 |

AC01不得用若干不相干输入拼成一份“全链成功”。它必须包含至少一个有真实网络元数据、已识别协议、已验证恢复内容且参与类型推理的输入。AC03提供额外的独立分类效果证据，不能替代AC01的分类接入。

分类指标门槛沿用原计划U4：macro-F1超过多数类基线，各类recall非零，同时披露小样本限制。大模型解释用确定性证据检查加人工复核，不要求两次生成文本完全相同；两次运行应保持事实、引用有效性和恢复哈希一致。

## Collaboration Rules

1. 开工时选定共同基线提交，并核对未提交/未跟踪文件。已有9月10日公共报告不丢弃；A在集成清单中注明是否纳入基线。不要从三台机器的不同状态各自开始。
2. 建议三个独立分支 `codex/acceptance-a-integration`、`codex/acceptance-b-recovery`、`codex/acceptance-c-behavior`，A维护 `codex/acceptance-integration`。本文只给出分支方案，不已创建分支或推送。
3. 每个交付批次包括代码、Schema、正反样例、测试结果、命令和已知限制；“写好了，稍后测试”不能算交付。先小批交接，避免晚上一次合并所有变更。
4. 本线单测由作者执行；消费者执行一次接口冒烟后接收；G4再跑全部模块及跨模块回归。更改失败范围后重测相关链路，不无理由重复全套。
5. 每个角色只写自己的 `docs/acceptance/status/<role>.md` 和 `docs/acceptance/handoffs/<role>.md`；A单独汇总 `docs/acceptance-taskboard.md`。按执行契约记录提交、命令和证据；未开始时不要建立“通过”的空记录。计划文件保持稳定。
6. 阻塞超过30分钟，报告具体输入、报错、已尝试事项、影响接口与可继续工作；A组织10分钟定位。根因属于谁的文件由谁修复。
7. 每次联调后记录一个明确的可运行版本。只有全链验收通过的版本才能作为演示候选，模块测试通过的版本不能冒充最终候选。
8. 合并冲突由文件负责人解决，消费者核对接口；禁止通过删除失败断言、降低验收标准或覆盖真值来消除红灯。

建议每日只固定G1/G2/G3/G4等交付点沟通，中间用任务板同步。A负责召集和集成，不拥有单方放宽验收标准的权限。

## Definition of Done

三人完成的判断仍以原计划为准：主正例全链、裸流/负例正确处理、独立分类证据、实际模型解释、可搬迁运行和完整提交材料全部具备。

最终签收必须有A确认入口和报告、B确认协议与恢复语义、C确认真值和独立评估；任何关键门禁未通过，任务板都保留未完成。计划中的期限或工作量比例不能覆盖这一规则。
