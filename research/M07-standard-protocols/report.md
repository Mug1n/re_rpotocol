# M7 标准协议识别与解析

状态：已实现/待完整集成。检索日期：2026-09-07；2026-09-08 已实现 TShark 字段白名单、契约校验、合法降级与确定性 fake 测试。

用途：优先用已有解析器识别标准协议，输出实际可见字段和解析依据。

| 候选 | 主要特点与优势 | 输入输出及前置条件 | 限制 | 来源 |
|---|---|---|---|---|
| Wireshark / TShark | 共用协议解析体系；前者适合人工查看，后者支持字段、JSON 等输出及 Decode As | 可识别抓包封装、网络会话及足够完整的协议数据 → 协议层次和字段 | 端口、启发式和 Decode As 均需结合实际字段判断；没有通用未知密文识别保证 | [TShark 手册](https://www.wireshark.org/docs/man-pages/tshark.html)、[官方协议字段索引](https://www.wireshark.org/docs/dfref/) |

覆盖与条件如下；“支持”指官方索引存在对应解析器，不表示任意抓包都能成功解析。

| 协议 | 可解析内容与必要条件 | 主要边界 |
|---|---|---|
| HTTP | 明文请求/响应及头部，跨 TCP 包时需要重组；索引还列有 HTTP/2、HTTP/3 | HTTPS 内层需要满足 TLS 解密条件，HTTP 各版本不能用同一文本规则概括 |
| SMTP、POP3、IMAP | 明文命令、响应及部分邮件相关字段；POP3 的过滤名为 pop | STARTTLS 后或隐式 TLS 内部内容不再直接可见 |
| FTP | 控制命令与响应，数据通道需关联相应连接 | 只有控制流不能还原文件；FTPS 与 SFTP 不等于明文 FTP |
| TLS | 未被加密的记录/握手信息及可见扩展 | 应用明文需要适用的会话密钥等条件；握手版本与加密扩展影响可见范围 |
| SSH | 版本交换和未加密的协商部分 | 加密开始后不能凭解析器恢复终端命令或 SFTP 内容 |
| DNS | 普通 DNS 查询/响应与记录；TCP 方式需要相应分帧 | DoT/DoH 的 DNS 内容受到外层加密限制 |

来源：[官方协议字段索引](https://www.wireshark.org/docs/dfref/)、[重组说明](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvReassemblySection)、[TLS 解密条件](https://wiki.wireshark.org/TLS)。表中关于缺失数据和外层加密的后果为本项目适用性判断。

初步建议：沿用 M1 的 TShark 分支，不为每个标准协议另找库。保留实际字段证据，并区分自动识别、用户指定 Decode As、解析失败与未知。非标准端口可以提供解析提示，但提示不是确认依据；端口号本身不能证明协议。

本地验证边界：确定性 fake 覆盖 HTTP、TLS、Decode As、裸字节、工具缺失和畸形输出；真实 DAT 的封装、目标协议版本和可见握手仍待课程数据核实。裸应用字节流需要先明确入口与格式，不能伪造 TCP/IP 头后把解析成功当原始事实。
